# 사용자 관심사 기반 콘텐츠 노출 자동화 PRD

> - **문서 버전:** 1.0
> - **작성자:** HelloBot PM Team
> - **최종 수정일:** 2025-08-22

---

## 1. 개요 (Overview)

_이 프로젝트는 모든 사용자에게 동일한 콘텐츠를 노출하는 비효율성을 해결하여 구매자 ARPPU 및 LTV 증대를 달성하기 위한 개인화 추천 시스템입니다. 이를 통해 사용자는 관심사에 맞는 맞춤형 콘텐츠를 효율적으로 발견할 수 있습니다._

- **이 시스템은**: “스킬(사주/타로 등) 노출 영역(홈배너·카테고리·섹션·검색)에 사용자 맞춤 콘텐츠를 노출”하고, **알고리즘을 실험(A/B)** 하며 **1주 LTV·클릭·전환**을 올리는 **개인화 추천 + 실험 플랫폼**입니다

---

## 2. 배경 및 문제 정의 (Background & Problem Statement)

- **문제 상황:**
  - 현재 모든 사용자에게 동일한 콘텐츠 구성을 노출하고 있어 개인화된 경험 제공 불가
  - 홈 메인배너(20슬롯), 카테고리(100슬롯), 섹션(30슬롯) 등 노출 지면 한계로 인한 콘텐츠 노출 기회 제약
  - 사주 콘텐츠의 특성상 1회 소비 후 재사용 가능성이 낮음에도 불구하고 주요 지면을 계속 차지
  - 구매 전환율이 높은 콘텐츠들이 노출 우선순위에 밀려 노출되지 않는 문제 발생
- **근거 자료:**
  - 현재 운영자 수동 운영으로 인한 노출 스킬의 운영자 기억 의존성
  - 신규 스킬 노출을 위해 기존 스킬 제외 시 매출 급감 현상 (카니발라이제이션)
  - 노출 지면 규모에 따른 매출 제한 효과 확인
- **기회:**
  - 개인화 추천을 통한 구매자 ARPPU/LTV 증대
  - 기존 생산 콘텐츠의 활용도 극대화
  - 경쟁사 대비 개인화 서비스 경쟁력 확보
  - 사용자마다 해당 사용자에 맞는 스킬 세트를 노출함으로써 더 많은 스킬을 노출 시킬 수 있음.
- **이슈**
  - 현재 어떤 알고리즘이 최적인지 알지 못한다. 알고리즘은 지속적으로 변할 수 있고, 개발하고 적용하고 테스트할 수 있어야 한다.

## 3. 목표 및 성공 지표 (Goals & Success Metrics)

_이 기능이 적용되면, 사용자는 자신의 관심사에 맞는 구매할만 한 더 많은 스킬을 만날 수 있으므로 진입하는 스킬의 수가 증가할 것이고, 이후 퍼널 전환율이 동일할 경우 구매가 증가할 것이다._

_들어올 때마다 매번 새로운 스킬을 보게 되면, 방문 리텐션도 올라갈 것이다._

- **상위 목표 (Business Goal):** 구매자 ARPPU/LTV 증대를 통한 총 매출 증가
- **제품 목표 (Product Goal):** 사용자 관심사 기반 개인화 콘텐츠 노출을 통한 사용자 경험 개선 - 사용자가 관심 있을만한 콘텐츠들을 노출
- **핵심 성공 지표 (Success Metrics):**
  - **주요 지표 (Primary Metric):** 구매자 ARPPU (1회 이상 구매한 사용자 대상)
  - **보조 지표 (Secondary Metrics):**
    - 사용자의 일 평균 조회 스킬수 증가
    - 사용자의 일 평균 진입 스킬수 증가
    - 1주/1개월 LTV 개선
- **가드레일 지표 (Guardrail Metrics):**
  - 사용자 경험 보호:
    - 홈 화면 로딩 시간: 기존 대비 +200ms 이내 유지
    - 앱 크래시율: 기존 수준 유지 (< 0.1%)
    - 사용자 이탈률(Churn Rate): 기존 대비 5% 이상 증가 금지
  - 매출 보호:
    - 전체 매출: 기존 대비 5% 이상 감소 금지
    - 핵심 스킬 매출: 개별 스킬 매출 30% 이상 감소 금지
    - 신규 사용자 전환율: 기존 대비 10% 이상 감소 금지
  - 운영 안정성:
    - 시스템 가용성: 99.9% 이상 유지
    - 추천 알고리즘 응답시간: 100ms 이내
    - 콘텐츠 노출 다양성: 상위 20% 스킬이 전체 노출의 80% 이상 차지 금지

## 4. 사용자 스토리 및 요구사항 (User Stories & Requirements)

  - 웹은 주로 신규 유입 or 마케팅으로 특정 스킬 랜딩으로 들어오는 사용자 → 바로 꽂아주는 것이 좋음
  - 앱으로 들어오는 사용자
- **사용자 스토리 (User Stories):**

  - **#1:** 신규 사용자로서, 관심사 정보가 없어도 인기 있는 콘텐츠를 추천받을 수 있다.
    - **요구사항 (Acceptance Criteria):**
      - [ ] 온보딩 설문을 통해 관심사 정보 수집

- **사용자/스킬 정보 수집 저장 및 관리 기능**

  - **수집 저장 및 관리 필요에 따른 구성 요소**
    - 사용자/스킬 정보 구조화
    - 실시간 관리 정보 / 배치 처리 정보 구분
  - 사용자 정보 수집 저장 및 관리 (사용자 정보로 부터 사용자의 세그먼트를 도출)
    - 고정적 정보 → 성별, 가입일 등
    - 변동되는 정보 → 최근 구매한 스킬, 총 구매 금액, 리텐션 주기 등
  - 스킬 정보 수집 저장 및 관리 (스킬 단위의 통계, 세그먼트 도출)
    - 고정적 정보 → 스킬 타입, 주제 등
    - 변동되는 정보 → 최근 구매자 수 등
    - 필터링에 사용될 정보를 운영자가 설정하고 관리할 수 있는 기능. (알고리즘에서 활용)
  - 피쳐 엔지니어링 : Raw Data를 가공하여 의미있는 Data 도출

    - 사용자, 스킬 Raw Data로부터 서비스에 바로 사용할 데이터로 변환하는 기능 → 서비스에서는 이 데이터를 활용
    - 피쳐 스토어 예시

      - **피처 스토어의 아키텍처 (카카오 '이그드라실' 사례):** 카카오의 광고 추천 시스템에 도입된 '이그드라실(Yggdrasil)'은 피처 스토어의 구조를 잘 보여줍니다.18
      - **오프라인 스토어 (Offline Store):** 대용량의 과거 피처 데이터를 저장합니다. 주로 모델 학습을 위한 데이터셋을 생성하는 데 사용되며, 하둡 분산 파일 시스템(HDFS)과 같은 대용량 스토리지 시스템을 기반으로 합니다.
      - **온라인 스토어 (Online Store):** 최신 피처 값을 저장하며, 실시간 추론(inference) 시 낮은 지연 시간(low latency)으로 피처를 조회할 수 있어야 합니다. 이를 위해 Redis나 Cassandra와 같은 고성능 Key-Value 데이터베이스가 주로 사용됩니다.

      **피처 레지스트리 (Feature Registry):**

      모든 피처의 정의, 메타데이터(데이터 타입, 설명 등), 버전 정보 등을 중앙에서 관리하는 카탈로그입니다.

  - 사용자/스킬 정보 예시
    - **명시적 데이터 (Explicit Data):** 사용자가 자신의 선호도를 직접적으로 표현한 데이터입니다. 품질이 매우 높고 해석이 명확하지만, 사용자의 적극적인 참여가 필요하기 때문에 수집량이 적은 경향이 있습니다.
      - **예시:** 평점(별점), 좋아요/싫어요, 리뷰, 구독 목록.
    - **암시적 데이터 (Implicit Data):** 사용자의 자연스러운 서비스 이용 과정에서 발생하는 행동 데이터로부터 선호도를 간접적으로 추론합니다. 데이터 양이 풍부하여 시스템의 기반을 이루지만, 해석에 노이즈가 낄 수 있다는 단점이 있습니다.
      - **예시:** 콘텐츠 조회/열람 기록, 시청/열람 시간 및 완료율, 클릭 기록, 검색어, 스크롤 깊이, '나중에 볼 목록' 추가 행위.
    - **콘텐츠 메타데이터 (Content Metadata):** 추천 대상이 되는 아이템 자체의 속성 정보입니다. 이 데이터는 콘텐츠 기반 필터링의 핵심이며, 협업 필터링의 콜드 스타트 문제를 완화하는 데에도 중요하게 사용됩니다.
      - **웹툰 예시:** 장르, 작가, 그림체, 연재 요일, 관련 태그(예: #회귀, #학원물), 줄거리.
      - **영상 예시:** 배우, 감독, 개봉 연도, 국가, 시놉시스.
    - **문맥 정보 (Contextual Information):** 사용자와 아이템의 상호작용이 발생하는 '언제, 어디서, 어떻게'에 해당하는 정보입니다. 동일한 사용자라도 문맥에 따라 선호도가 달라질 수 있기 때문에, 추천을 개인화하는 데 중요한 단서를 제공합니다.
      - **예시:** 접속 시간(아침/저녁), 요일(주중/주말), 사용 기기(모바일/PC), 접속 위치.

- **사용자 세그먼트 판단 기능**
  - 사용자가 들어왔을 때, 해당 사용자의 세그먼트를 판단하는 기능
- (Adv.) 사용자의 실시간 정보를 수집하고, 알고리즘에 반영하는 기능
- 추천 파이프라이닝 - 랭킹 알고리즘 (규칙)

  - 추천 파이프라이닝 예시

    ### **3.1. 1단계: 후보군 생성 (Candidate Generation)**

    추천 파이프라인의 가장 첫 번째 단계인 후보군 생성은 방대한 전체 아이템 코퍼스(수백만 ~ 수십억 개)에서 사용자가 관심을 가질 만한 수백 개 정도의 후보 아이템을 신속하게 추려내는 것을 목표로 합니다. 이 단계의 핵심 성능 지표는 속도(latency)와 재현율(recall)입니다. 즉, 얼마나 빠르게, 그리고 놓치는 좋은 아이템 없이 후보군을 잘 만들어내는지가 중요합니다. 정확성(precision)은 다음 단계에서 보정하므로, 여기서는 다소 거칠더라도 잠재력 있는 후보들을 최대한 많이 포함하는 것이 중요합니다.

    ### **주요 기술**

    - **극단적 다중 클래스 분류 (Extreme Multiclass Classification):** 유튜브가 사용하는 대표적인 접근법으로, 추천 문제를 '사용자의 다음 시청 동영상을 전체 동영상 중에서 맞추는' 초거대 분류 문제로 정의합니다.16 이 과정에서 모델은 사용자와 동영상에 대한 강력한 임베딩 벡터를 학습하게 되며, 이 임베딩을 활용하여 특정 사용자에 대해 관련성 높은 동영상 후보군을 빠르게 검색할 수 있습니다.
    - **벡터 유사도 검색 (Vector Similarity Search):** 아이템 임베딩을 미리 계산해 둔 상태에서, 사용자의 현재 관심사를 나타내는 쿼리 벡터(query vector)와 '가장 가까운' 아이템들을 찾는 방식입니다. 전체 아이템과 일일이 거리를 계산하는 것은 비효율적이므로, 근사 최근접 이웃(Approximate Nearest Neighbor, ANN) 탐색 알고리즘을 사용합니다. 구글의 ScaNN(Scalable Nearest Neighbors)이나 Faiss 같은 라이브러리는 수억 개의 벡터 중에서도 수 밀리초 내에 근사적으로 가장 유사한 벡터들을 찾아낼 수 있어, 대규모 후보군 생성에 필수적인 기술로 자리 잡았습니다.20
    - **경량 협업 필터링 (Lightweight Collaborative Filtering):** 미리 계산된 아이템-아이템 유사도 행렬(e.g., 'A 웹툰을 본 사람이 많이 본 웹툰 목록')이나 사용자-아이템 상호작용 기록을 기반으로 한 간단한 규칙 기반 또는 모델 기반의 필터링을 적용하여 빠르게 후보군을 추출합니다.

    ### **3.2. 2단계: 랭킹 (Ranking)**

    후보군 생성 단계를 통과한 수백 개의 아이템들은 이제 랭킹 단계로 넘어옵니다. 이 단계의 목표는 후보 아이템들에 대해 훨씬 더 정밀한 개인화 점수를 매겨, 사용자에게 최종적으로 보여줄 최적의 순서를 결정하는 것입니다.16 후보군의 크기가 대폭 줄었기 때문에, 이 단계에서는 계산 비용이 더 높더라도 정확도(precision)가 뛰어난 복잡한 모델과 풍부한 피처를 사용할 수 있습니다.

    ### **모델 및 피처**

    - **정교한 딥러닝 모델:** 이 단계에서는 Wide & Deep, Neural Collaborative Filtering, 혹은 도메인 특화된 복잡한 딥러닝 모델들이 주로 사용됩니다. 후보군 생성 단계에서는 사용하기 어려웠던 다양한 실시간 문맥 피처와 복잡한 피처 교차(feature cross)를 활용하여 사용자의 선호를 매우 정밀하게 예측합니다.16
    - **풍부한 피처 활용:** 랭킹 모델은 후보군 생성 모델보다 훨씬 다채로운 정보를 활용합니다. 예를 들어, '사용자가 이 웹툰의 작가 다른 작품을 본 적이 있는가?', '이 영화의 주연 배우가 출연한 다른 영화를 최근에 봤는가?', '현재 시간대에 이 장르의 소비가 증가하는가?'와 같은 상세하고 동적인 피처들이 모델의 입력으로 사용됩니다.16

    ### **최적화 목표 함수 (Objective Function)**

    랭킹 모델이 무엇을 예측하도록 학습되는지는 서비스의 목표와 직결되는 매우 중요한 결정입니다. 단순히 '클릭률(Click-Through Rate, CTR)'을 예측하는 것은 사용자가 제목이나 썸네일에 낚여 클릭했지만 내용은 만족스럽지 않은 '클릭베이트(clickbait)' 콘텐츠의 순위를 높이는 부작용을 낳을 수 있습니다. 이를 방지하기 위해 유튜브와 같은 선도적인 플랫폼들은 '예상 시청 시간(predicted watch time)'을 주요 최적화 목표로 삼습니다.16 이는 단순히 클릭을 유도하는 것을 넘어, 사용자가 콘텐츠를 실제로 얼마나 오래, 만족스럽게 소비하는지를 예측함으로써 추천의 질을 높이려는 전략적 선택입니다.

    ### **3.3. 3단계: 재랭킹 및 필터링 (Re-ranking and Filtering)**

    랭킹 모델이 매긴 점수 순서가 그대로 사용자에게 노출되는 경우는 드뭅니다. 마지막 단계에서는 비즈니스 규칙, 공정성, 사용자 경험의 질적 측면을 고려하여 최종 목록을 한 번 더 조정합니다.19

    ### **주요 조정 작업**

    - **필터링 (Filtering):** 사용자가 이미 소비한 콘텐츠, 명시적으로 '싫어요'를 표시한 콘텐츠, 또는 연령 등급에 맞지 않는 부적절한 콘텐츠를 최종 목록에서 제외합니다.
    - **다양성 (Diversity) 확보:** 추천 목록이 한 가지 장르나 특정 작가의 작품으로만 채워지는 것을 방지합니다. 상위 N개의 아이템 간의 유사도를 측정하여, 너무 비슷한 아이템이 연달아 나오지 않도록 순서를 조정하거나 일부를 다른 아이템으로 교체합니다. 이는 사용자의 만족도와 새로운 발견의 기회를 높이는 데 매우 중요합니다.23
    - **신선도 (Freshness) 증진:** 새로 등록된 콘텐츠가 사용자에게 발견될 기회를 가질 수 있도록 점수에 가산점을 부여(boosting)합니다. 플랫폼 생태계의 활력을 유지하기 위해 필수적인 장치입니다.16
    - **공정성 및 비즈니스 규칙 적용 (Fairness & Business Rules):** 특정 작가나 콘텐츠 제공자에게 노출 기회가 공정하게 돌아가도록 조정하거나, 프로모션 대상 콘텐츠의 순위를 높이는 등 비즈니스 목표에 따른 규칙을 적용합니다.

    이러한 다단계 아키텍처는 '수십억 개 중에서 가장 관련성 높은 것 찾기'라는 거대한 문제를 '관련성 있는 수백 개 찾기'와 '수백 개 중에서 가장 좋은 것 찾기'라는 두 개의 다루기 쉬운 문제로 분리하는 탁월한 접근법입니다. 후보군 생성 단계는 속도를 위해 근사(approximation)를 허용하는 정보 검색 기술에 가깝고, 랭킹 단계는 정확도를 극대화하는 정밀한 머신러닝 모델링에 가깝습니다. 이처럼 각 단계의 역할과 제약 조건을 명확히 분리하고 그에 맞는 최적의 기술을 적용하는 것이 넷플릭스나 유튜브 규모의 개인화를 실시간으로 가능하게 하는 핵심적인 아키텍처 패턴입니다.

  - 기본 규칙 기반 랭킹 (Default) - 콜드 스타트 / 사용자 정보가 없는 경우 노출 우선순위
  - 추천 대상 스킬 (노출 가능한 후보 선정) - 노출에 필요한 정보를 갖추고 있는 스킬
  - 필터링
    - 사주 & 이미 본 스킬 제외
    - 무료스킬 제외
  - 우선순위 정렬
    - 랭킹 - 스킬간 노출 우선순위 계산 로직. 통계기반 자동 랭킹.
    - 재랭킹 규칙 - 운영자 가중치, 캠페인, 슬롯별 제약, 이미 본 스킬 제외, 신규스킬 우대 등을 반영

- 스킬 추천 목록 API 백엔드

  - 스킬 추천 파이프라인 예시

    현대 추천 시스템의 데이터 흐름은 실시간 스트림 처리와 배치 처리가 유기적으로 결합된 복잡한 파이프라인을 통해 이루어집니다. 사용자의 작은 행동 하나가 시스템 전체를 거쳐 어떻게 다시 개인화된 경험으로 돌아오는지 시각화하면 다음과 같습니다.

    - **1. 이벤트 발생 및 수집:** 사용자가 앱에서 웹툰을 클릭하거나, 영상을 시청하는 등 행동을 취하면, 클라이언트(앱/웹)는 해당 이벤트 로그를 생성하여 이벤트 수집 서버로 전송합니다.
    - **2. 실시간 이벤트 스트리밍:** 수집 서버는 받은 이벤트를 대용량 메시지 큐 시스템인 **아파치 카프카(Apache Kafka)**와 같은 이벤트 버스(Event Bus)에 즉시 발행(publish)합니다. 카프카는 초당 수백만 건의 이벤트를 안정적으로 처리하며, 데이터 생산자(클라이언트)와 소비자(처리 엔진)를 분리(decoupling)하는 완충 역할을 합니다.
    - **3. 스트림 처리 및 실시간 피처 업데이트:** **아파치 스파크 스트리밍(Spark Streaming)**이나 **아파치 플링크(Flink)**와 같은 분산 스트림 처리 엔진이 카프카의 이벤트를 실시간으로 구독(subscribe)하여 처리합니다. 이 단계에서는 간단한 집계(예: 최근 10분간 특정 웹툰의 클릭 수)를 수행하여 '실시간 트렌드' 피처를 계산하거나, 사용자 프로필(예: '최근 본 작품 목록')을 업데이트합니다.
    - **4. 피처 저장소 업데이트:** 스트림 처리 엔진이 계산한 최신 피처 값은 **피처 스토어(Feature Store)**의 온라인 저장소(예: Redis, Cassandra)에 기록됩니다. 동시에, 원시 로그와 처리된 데이터는 장기 분석 및 모델 학습을 위해 **HDFS**나 클라우드 스토리지(AWS S3 등)와 같은 데이터 레이크(Data Lake)에 저장됩니다.
    - **5. 추천 요청:** 사용자가 홈 페이지에 진입하면, 클라이언트는 백엔드의 **추천 API 서버**에 개인화된 콘텐츠 목록을 요청합니다.
    - **6. 실시간 추론(Inference):**
    - **a. 피처 조회:** 추천 API 서버는 요청한 사용자의 ID를 기반으로 피처 스토어의 온라인 저장소에서 필요한 피처(예: 사용자 임베딩, 최근 선호 장르)를 매우 낮은 지연 시간으로 조회합니다.
    - **b. 후보군 생성:** 조회된 피처를 입력으로, **후보군 생성 모델**이 수백 개의 관련 아이템 ID를 빠르게 반환합니다.
    - **c. 랭킹:** 생성된 후보 아이템들에 대한 상세 피처를 추가로 조회한 후, **랭킹 모델**이 각 아이템의 최종 점수를 계산합니다.
    - **d. 재랭킹:** 비즈니스 로직에 따라 최종 목록을 조정합니다.

    **7. 추천 결과 반환:**

    최종적으로 정렬된 아이템 ID 목록이 클라이언트에 반환되고, 클라이언트는 이 ID에 해당하는 메타데이터(제목, 썸네일 등)를 별도의 메타데이터 서비스에서 조회하여 화면에 렌더링합니다.

  - 연산 계층

    모든 계산을 실시간으로 처리하는 것은 비효율적이며 불필요합니다. 넷플릭스는 연산 작업을 요구되는 응답 시간에 따라 세 가지 계층(Tier)으로 구분하는 영향력 있는 아키텍처를 제시했습니다. 이는 시스템의 복잡성과 비용을 관리하면서도 사용자에게 높은 수준의 반응성을 제공하기 위한 실용적인 설계 철학입니다.31

    - **오프라인 (Offline):** 실시간 제약이 전혀 없는 배치(batch) 작업입니다. 수 시간 또는 하루에 한 번 주기로 실행됩니다. 데이터의 양이나 알고리즘의 복잡성에 거의 제약이 없으므로, 대규모 데이터셋을 사용한 복잡한 딥러닝 모델의 학습이나, 자주 변하지 않는 데이터(예: 아이템 간 유사도 행렬)의 사전 계산에 주로 사용됩니다. 새로운 알고리즘을 실험하고 검증하기에 용이하다는 장점이 있습니다.31
    - **니어라인 (Nearline):** 사용자의 특정 행동에 의해 트리거되지만, 즉각적인 동기적(synchronous) 응답이 필요 없는 비동기(asynchronous) 작업입니다. 예를 들어, 사용자가 한 편의 웹툰 감상을 완료했을 때, 이 이벤트를 받아 몇 초 또는 몇 분 내에 해당 사용자의 장르 선호도 프로필을 업데이트하는 작업이 여기에 해당합니다. 오프라인보다 훨씬 최신 데이터를 반영할 수 있으면서도, 온라인의 엄격한 지연 시간 제약에서는 자유롭습니다.

    **온라인 (Online):**

    사용자 요청에 대해 수십 밀리초(ms) 내에 실시간으로 응답해야 하는 작업입니다. 추천 파이프라인의 마지막 단계인 피처 조회, 후보군 생성, 랭킹, 재랭킹 등이 모두 이 계층에 속합니다. 지연 시간 제약이 매우 엄격하므로, 계산 복잡도가 높은 작업은 피하고, 대부분의 계산 결과를 미리 준비된 상태에서 빠르게 조회하고 조합하는 방식으로 동작합니다.31

  - 분류된 사용자를 데이터에서 구분해서 볼 수 있는 기능 (분류된 결과값이 데이터에 기록)
- 배포 기능
  - 변경된 알고리즘을 특정 일시부터 적용하는 기능
  - 변경된 알고리즘을 서비스에서 테스트 할 수 있는 기능
- A/B 테스트의 진행상황과 결과를 확인할 수 있는 대시보드
- 안정성 기능
  - 개인화 추천 인프라 중 하나라도 이상이 생겼을 경우, 기존 캐싱된 결과로 서빙하고, 그런 데이터가 없는 경우에도 Default 세팅으로 서빙된다.
  - 개인화 추천 인프라 중 하나라도 이상이 생겼을 경우, 운영자가 인지하여 조치할 수 있도록 알림 기능이 있어야 한다. (잘못된 알고리즘으로 계속 서비스 될 경우 성과가 급격히 하락하게 될 수 있다)

## 5. 범위 (Scope)

**_1차 목표: 홈 메인배너의 스킬 노출을 기본, A그룹, B그룹으로 복수의 노출 알고리즘을 설정하고, A/B 테스트 할 수 있는 기능 구현. 알고리즘은 최대한 간단한 것으로 구현하고, 추후 알고리즘 추가가 용이한 구조 구축._**

- **In Scope (포함 범위):**
  - [ ] ✅ 사용자/스킬 정보 수집 저장 및 관리 기능
    - [ ] ✅ 사용자 정보 구조화
    - [ ] ✅ 스킬(콘텐츠) 세그먼트 정보 구조화 (주제, 타입 등)
    - [ ] ✅ 운영자 선정 콘텐츠 우선 노출 로직을 위한 정보 구조
  - [ ] ✅ 사용자 세그먼트 판단 기능
  - [ ] (Adv.) 사용자의 실시간 정보를 수집하고, 알고리즘에 반영하는 기능
  - [ ] ✅ 추천 파이프라이닝 - 랭킹 알고리즘 (규칙)
    - [ ] ✅ 기본 추천 콘텐츠 판별 로직 (신규 사용자용)
    - [ ] 사용자 개별 추천 콘텐츠 판별 로직 (개인화)
  - [ ] ✅ 스킬 추천 목록 API 백엔드
    - [ ] ✅ 추천 엔진으로부터 사용자별 스킬 목록을 가져와서 보여주는 기능
  - [ ] ✅ 노출 지면별 알고리즘 설정 기능 / 실험 관리 기능
    - [ ] ✅ 홈 메인배너
    - [ ] 카테고리
    - [ ] 섹션
    - [ ] 검색
  - [ ] ✅ A/B 테스트 기능
    - [ ] ✅ 홈 메인배너의 알고리즘을 2종이상 등록하고, A/B 테스트 하는 기능
  - [ ] 배포 기능
    - [ ] ✅ 무중단 배포
    - [ ] ✅ 사용자 배포 전 운영환경에서 동작을 테스트 해볼 수 있는 기능 (테스터에만 적용 등)
  - [ ] ✅ A/B 테스트의 진행상황과 결과를 확인할 수 있는 대시보드
  - [ ] ✅ 안정성 기능
    - [ ] ✅ 홈 배너 노출 속도 지연 최소화
- **Out of Scope (제외 범위):**
  - [ ] 복잡한 노출 알고리즘 구현 → 노출 알고리즘을 여러개 사용자 그룹별로 적용할 수 있도록 하는 것이 1차 목표. 알고리즘 개발은 2차 이후 진행.
  - [ ] 실시간 머신러닝 모델 적용
  - [ ] 사용자 행동 데이터 기반 실시간 학습

## 6. 현재 상태 분석

목표 지표에 대한 현재 상태값 조사. 조사해야 하는 데이터 항목만 나열하고, 실제 조사값은 개별적으로 조사하여 업데이트

- 목표 지표
  - **상위 목표 (Business Goal):** 앱 구매자 ARPPU/LTV 증대를 통한 총 매출 증가
  - **제품 목표 (Product Goal):** 사용자 관심사 기반 개인화 콘텐츠 노출을 통한 사용자 경험 개선 - 사용자가 관심 있을만한 콘텐츠들을 노출
  - **핵심 성공 지표 (Success Metrics):**
    - **주요 지표 (Primary Metric):** 구매자 ARPPU (1회 이상 구매한 사용자 대상)
    - **보조 지표 (Secondary Metrics):**
      - 사용자의 일 평균 조회 스킬수 증가
      - 사용자의 일 평균 진입 스킬수 증가
      - 1주/1개월 LTV 개선
  - **가드레일 지표 (Guardrail Metrics):**
    - 사용자 경험 보호:
      - 홈 화면 로딩 시간: 기존 대비 +200ms 이내 유지
      - 앱 크래시율: 기존 수준 유지 (< 0.1%)
      - 사용자 이탈률(Churn Rate): 기존 대비 5% 이상 증가 금지
    - 매출 보호:
      - 전체 매출: 기존 대비 5% 이상 감소 금지
      - 핵심 스킬 매출: 개별 스킬 매출 30% 이상 감소 금지
      - 신규 사용자 전환율: 기존 대비 10% 이상 감소 금지
    - 운영 안정성:
      - 시스템 가용성: 99.9% 이상 유지
      - 추천 알고리즘 응답시간: 100ms 이내
      - 콘텐츠 노출 다양성: 상위 20% 스킬이 전체 노출의 80% 이상 차지 금지
- **조사 대상 지표:**
  - 대상: 앱 구매 사용자 기준
  - 기간: 2025-06-16 ~ 2025-08-17
  - 현재 구매자 ARPPU (1회 이상 구매한 사용자 대상)
    - ARPPU: 20,500 ~ 23,000
      - 건당 구매 금액: 10,000 ~ 11,000
      - 인당 구매 횟수: 2.0 ~ 2.13
  - 사용자의 일 평균 조회 스킬수: 2.5 ~ 2.8
  - 사용자의 일 평균 진입 스킬수: 4.0 ~ 4.4
  - 1주/1개월 LTV
    - 1주: 20,500 ~ 23,000원
    - 1개월: 27,000(비시즌) ~ 32,000원(시즌)
- **현재 운영 방식 분석:**
  - 홈 메인 배너: 주 단위 운영자 수동 선정 (20슬롯)
  - 카테고리: 반기/연 1회 운영자 수동 선정 (100슬롯)

  - 모든 사용자에게 동일한 콘텐츠 노출

  - 신규 스킬 노출 시 기존 스킬 매출 급감 (카니발라이제이션)

  - 콘텐츠 생산 증가 대비 매출 증가 효과 제한
